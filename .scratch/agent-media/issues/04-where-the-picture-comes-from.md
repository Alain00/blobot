# Where does the picture come from, and does blobot ever take it itself?

## Question

*Send me a screenshot of how my app looks* has at least three mechanisms behind it, and they
differ in who holds the shutter. This is the crux of the map: almost every other ticket is
downstream of it.

1. **A tool result blobot observes.** The agent calls a browser server the operator configured, it
   returns an image block, blobot reads it off `tool_call_update` and draws it. blobot builds
   nothing, vouches for nothing new, and owns nothing. It also controls nothing: the picture
   exists because the operator installed a server, and blobot cannot say when it was taken or of
   what.
2. **A file the agent wrote in its own AgentWorkspace.** The agent runs a screenshot command or a
   Playwright script, a PNG lands in the worktree, and the agent points at it. blobot would read a
   path inside a workspace it already owns, which is the one directory the isolation argument does
   *not* fence off. Cheap, and it drags a path back into a story ADR-0004 spent its length getting
   paths out of.
3. **A tool of blobot's own**, on the loopback server beside `message_agent`, `propose_routine`
   and `record_entry`. The agent asks blobot to show something, and blobot decides what crosses,
   measures it, times it, and frames it. blobot holds the shutter, or at least the envelope.

## What it has to settle

- **Which of the three, or which combination.** They are not exclusive: 1 may be free and worth
  taking regardless, while 3 is the only one that can answer ticket 07 at all. Argue whether the
  cheap one and the good one are the same feature or two.
- **Whether 2 is refused, and on what grounds.** The reflex is that a path inside the agent's own
  workspace is fine, because that is precisely what the workspace is for. Grill it: the path is
  supplied by the agent, blobot would be reading a file chosen by the thing it is supervising, and
  `../` is a string. If it is allowed, the containment check is a decision, not an implementation
  detail.
- **What a blobot tool would actually be for.** *Show the user this* is not a screenshot tool.
  blobot cannot drive a browser, and it must not: that would put a headless browser in a
  local-first desktop app that ships no such thing. So option 3 is an **envelope**, not a camera,
  and the ticket should say so or reject the option.
- **Whether the answer depends on ticket 01's findings.** If a runtime rewrites images into paths
  on the wire, option 1 partly collapses into option 2 and this ticket has to handle it.
- **The honest ceiling on what the objective can deliver.** If the answer is 1, then *sends me back
  screenshots of how my app looks* is true only for a user who has a browser MCP server installed,
  and blobot's part is to stop discarding the result. That is a much smaller feature than the
  sentence implies, and if it is the right one it should be stated in the answer rather than
  discovered by the first person who tries it.

## What is binding

- **blobot is not a browser.** No headless browser, no page driving, no rendering engine beyond the
  Electron window it already is.
- ADR-0003 stands: the operator's own MCP servers load, and blobot does not curate them.
- Nothing here writes into an AgentWorkspace. A file left in a checkout can be committed home.
- If a new loopback tool is proposed, it inherits every rule the existing three have: named
  `blobot`/`<tool>`, the bearer token is the caller's identity, stateless, and every call it makes
  is disclosed in the turn that made it.

## Answer

**Option 3 is impossible, and 1 and 2 are both taken because they are two different features.**
Resolved 2026-09-05 against ticket 01's measurements. One sub-decision is left explicitly to the
author and is marked at the end.

### Option 3 cannot carry bytes, and that is not a preference

The ticket asked whether a blobot tool would be a camera or an envelope, and expected the answer
*envelope*. It is neither, because an envelope this shape cannot be filled.

**An MCP tool's arguments are generated by the model.** For an agent to hand blobot a picture
through `show_picture(...)`, the base64 would have to be emitted as output tokens. A 500 KB
screenshot is roughly 680,000 base64 characters. That is not expensive, it is not possible: no
model will reproduce it, and a model that tried would produce a corrupt image with no way to tell.
The only thing an agent can put in a tool call is **a reference**, and a reference is option 2.

So the three options are really two, and this is a permanent structural fact rather than a
judgement about today's models. Recorded here so nobody proposes the envelope again.

### Option 1 is taken, and it is the fix rather than the feature

Ticket 01 measured it working byte-exact on three of four runtimes, and ACP's own content design
exists to forward MCP tool output untransformed. blobot is already being handed these pictures and
deleting them.

But it is **not** the objective, and the gap should be stated where somebody will read it:

- It only happens if the operator installed a server that takes screenshots. blobot builds
  nothing, offers nothing, and cannot make it happen.
- It is **irrecoverable on fx**, which stringifies the result and truncates it at 200 characters
  mid-base64. There is no reader that fixes that. Ticket 10 draws it as a picture that arrived and
  could not be read, and that is the whole of the remedy.
- blobot knows almost nothing about the picture: the tool's name, the `toolCallId`, the agent, and
  the moment the update arrived. `annotations` are stripped, so there is no `lastModified` and no
  `audience`. It cannot say what was photographed or when.
- The model may not even have received it (OpenCode).

So option 1 is **the silent drop fixed**: draw what already arrives, with the little that is known
about it. It is cheap, it is honest, and it ships first because it is a defect.

### Option 2 is taken, and it is the objective

*A coding agent that sends me back screenshots of how my app looks* is a **deliberate act**, and
option 1 cannot express one: it is a side effect of a tool the agent called for its own reasons.
Option 2 is the agent choosing to show you something.

It also wins on every axis the measurements opened up:

- **It works on all five runtimes**, including fx, because the picture never travels on the ACP
  wire at all. The tool call carries a path and returns a short acknowledgement, which is well
  inside fx's 200 characters.
- **It sidesteps the model entirely.** OpenCode's model refused an image it was handed; under
  option 2 nothing asks the model to consume one. The picture goes from the filesystem to blobot's
  store to the screen, and the agent's context pays nothing but the path.
- **It is the only option that can answer ticket 07.** Reading the file itself, blobot knows the
  path, the byte size, the mtime, the dimensions, that it decoded, and that it was inside this
  agent's AgentWorkspace. Those are facts blobot **measured**. Under option 1 every fact except
  the arrival time is the runtime's word. Since ticket 01 established there is no third category
  between *measured* and *claimed*, this is what decides the ticket.

### Option 2's containment check, and what it is actually protecting

The path is supplied by the agent and `../` is a string, so it is checked against the agent's own
AgentWorkspace, resolved, with symlinks followed before the comparison.

The reason is **not** confidentiality. Ticket 02 settled that the user owns everything in reach and
is the recipient, and an agent that reads a file and shows it to its owner has leaked nothing.
The reason is narrower and better:

> blobot must not become a read primitive that bypasses the permission posture.

Every other read an agent performs goes through its runtime, where ticket 14's posture applies. A
tool that reads any path blobot can reach would be a way around that, in blobot's own voice, on
blobot's own authority. The check exists so that `show_user` cannot do anything the agent could not
already have done itself.

Note also that this makes blobot read a file **chosen by the thing it is supervising**, which is
new. It is acceptable only because the read is bounded to the workspace and the result is shown to
the owner, and both halves of that are load-bearing.

### What the tool is, and what it is not

One loopback tool beside `message_agent`, `propose_routine` and `record_entry`, inheriting all
their rules: named `blobot`/`<tool>`, the bearer token is the caller's identity, stateless, and
every call disclosed in the turn that made it.

It takes a **path** and a short **caption**, and it is not a camera. blobot does not drive a
browser, does not run a screenshot command, and does not have a rendering engine beyond its own
window. Whether the agent may take the picture in the first place is entirely ticket 05's, and if
that ticket says no at a given trust level, this tool has nothing to point at, which is correct.

The caption is the **agent's claim** and must never draw as blobot's. Ticket 07 owns that
distinction; it is named here only so the tool's shape does not quietly decide it.

### The consequence nobody gets to skip

Under option 2 the agent writes a PNG into its AgentWorkspace, which is a checkout of the user's
repository. **Screenshots accumulate as untracked files in a worktree, and a file left in a
checkout can be committed home.** That is the same hazard ticket 14 refused a settings file over
and ADR-0004 refused copying an attachment in over, and it is not avoided here, it is accepted.

The obvious escape is worse. Letting the agent write to a temp directory, or to a blobot-owned
per-agent directory the way handoffs live under `~/.local/share/blobot/handoffs/`, means blobot
reading outside the AgentWorkspace, which destroys the containment argument above and turns the
tool into the read primitive it was designed not to be. The workspace is the only place both
parties already agree on.

blobot does not write to `.gitignore`. That is the user's file.

**Left to the author.** Whether blobot should *delete* the file after reading it. It would keep
the worktree clean and it means blobot writing to the user's checkout by removing from it, which
is a different rule than the one about adding, and nobody has decided it. Recommended as a
separate ticket rather than answered here, because the argument for deleting a file an agent just
made is not obviously weaker or stronger than the argument for leaving the agent's own work alone.

### Order

1. **Option 1**, as ticket 10's silent-drop fix. It is a defect, it is small, and it is true today.
2. **Option 2**, as the feature, with ticket 07's frame on it.

They are not stages of one thing and should not be built as if they were. One is a transcript
telling the truth about what arrived; the other is an agent showing you something on purpose.

## Note, 2026-09-05: agent-browser confirms the option order

Raised by the author: `vercel-labs/agent-browser`, Apache-2.0, a native Rust CLI for driving a
browser, installed with `npm i -g agent-browser` or `brew`, plus `agent-browser install` to fetch
Chrome for Testing. It offers **both** of this ticket's options, which makes it the cleanest
available test of the ordering decided above.

- As `agent-browser mcp` it is an MCP server, and a screenshot comes back as an image content
  block. That is **option 1**, with everything option 1 has: four runtime shapes, irrecoverable on
  fx, a permission prompt per call because the server is the operator's, and blobot knowing only a
  tool name and an arrival time.
- As `agent-browser screenshot shots/login.png` it is a command writing a file into the agent's own
  working directory, which is its AgentWorkspace. That is **option 2**, and the loopback tool then
  points at the file.

The same vendor, the same browser, the same pixels, and the second path is better on every axis
this ticket already used: it works on fx, the model never has to consume the image, and blobot
opens the file itself so ticket 07's frame is measured rather than claimed. Recorded because it is
the first concrete tool that makes the choice visible instead of hypothetical, and it changes
nothing.

It is **not** a dependency this map takes on. blobot builds nothing, installs nothing and names no
browser; the objective is that an agent can show a picture it made, by whatever means it has.
