# Docker Engine versus sbx: isolation, egress and product constraints

Research for [Docker Engine and sbx: isolation, network access and product constraints](../issues/21-engine-isolation-egress-and-product.md), 2026-09-05. This is evidence for the later human reevaluation, **not an engine selection or permission to weaken a boundary**. Lifecycle/resource measurements belong to the [companion research](16-engine-lifecycle-persistence-and-costs.md); this document explains the security and product cost behind those figures.

## Result

Ordinary Docker Engine is a credible simpler persistence/resource backend, but it is not an equivalent implementation of the currently chosen **microVM per Agent**. Containers offer real isolation; rootless execution strengthens it. Neither gives each Agent its own kernel. Reproducing sbx's private Docker daemon and mandatory selective egress adds machinery beyond create/exec/stop. Conversely, sbx's integrated isolation does not remove ownership checks, image supply-chain work, login integration, recovery, or the risks of deliberately shared files and allowed network destinations. These are architectural inferences from the capabilities below, not measured security scores.

The binding inputs are [What a Machine is](../issues/01-what-a-machine-is.md#answer-2026-09-04), including its amendments, and the final answers on [lifecycle/setup](../issues/19-a-box-lifecycle-and-engine-setup.md#answer--2026-09-05) and [scoped readiness](../issues/08-detection-and-remedies-per-machine.md#answer--2026-09-05). The microVM choice and closed host-access list are already decisions. The detailed [highest trust level](../issues/10-does-a-machine-answer-the-fourth-level.md) and [egress policy](../issues/15-egress-from-a-box.md) remain open; their proposals are not completed implementation or blanket authorization for unrestricted tools.

## Threat/capability matrix

Assume a malicious repository, dependency install or compromised CLI can run arbitrary code **inside its Agent's environment**. The trusted desktop/engine administrator remains outside that adversary model. Neither route can protect an Agent from an administrator with authority over its engine, mounts and policy.

| Boundary or capability | Ordinary Engine, rootful daemon | Rootless Engine | sbx microVM |
| --- | --- | --- | --- |
| Kernel exposure [D] | Container namespaces/capabilities restrict processes sharing the daemon host's Linux kernel | User namespace also makes daemon and containers non-root; still the same kernel | Separate Linux kernel per sandbox; guest sudo is inside the hypervisor boundary |
| On macOS [D/I] | Desktop's Linux VM separates containers from macOS, but sibling Agents share that VM's kernel | Requires a Linux environment too; changing daemon UID is not a per-Agent VM | One microVM per Agent without Desktop or host Engine |
| Guest root [D/I] | Root with reduced capabilities is not host root; privileged mode substantially changes the boundary | Root maps into subordinate host IDs; not unrestricted host root | Agent has sudo and its own Docker Engine; VM boundary remains load-bearing |
| Sibling files [D/I] | Separate mounts/namespaces; daemon API or incorrect mounts can defeat them | Same requirement; shared daemon access still controls its containers/data | Private guest filesystem; explicit shares remain exceptions |
| Sibling network [D] | Default same-bridge peers can communicate; dedicated networks alone are not a complete host-service policy | Requires explicit network design and compatible rootless networking | Direct sandbox-to-sandbox networking documented blocked |
| Selective mandatory egress [D] | Engine primitives, not a built-in sbx-style domain policy service | Same absence; implementation must fit rootless network backend | Forward and transparent proxy paths enforce policy; direct external UDP/ICMP blocked |
| Readiness/admission [I/O] | Rich inspect API can support checks, but effective firewall/profile validation remains work | Also check rootless mode and actual cgroup delegation | Current recorded-ID/observable checks work on fixtures, but incomplete image/config inspection remains accepted limitation |

Sources: [Engine security](https://docs.docker.com/engine/security/), [rootless architecture](https://docs.docker.com/engine/security/rootless/), [Desktop architecture](https://docs.docker.com/desktop/features/networking/), [sbx isolation](https://docs.docker.com/ai/sandboxes/security/isolation/), [bridge behavior](https://docs.docker.com/engine/network/drivers/bridge/), and [prior RC5 admission](10-sbx-rc5-engine-admission.md).

### Hardening is useful, and changes the workload contract

**[D]** Docker uses a syscall allowlist by default where seccomp is available; its docs advise retaining that protection. AppArmor's default profile protects containers, not the Docker daemon, and depends on platform support. **[I]** A candidate untrusted-Agent container would additionally need an explicit user, minimal capabilities, no host PID/network namespace, no host devices/socket/signing agent, bounded processes/resources, and constrained mounts. `no-new-privileges` and a capability-free non-root process conflict with promising unrestricted sudo/package administration: decide the actual workload before selecting flags. This is not a tested launch recipe. [Seccomp](https://docs.docker.com/engine/security/seccomp/), [AppArmor](https://docs.docker.com/engine/security/apparmor/), [run privileges](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities).

**[D]** Rootless resource enforcement requires cgroup v2 and systemd; otherwise relevant Docker flags can be ignored. CPU controller delegation can require host administration. Current rootless limitations include no AppArmor support, checkpoint or overlay network, and storage-driver constraints. **[I]** For Guillermo's hard CPU/RAM maxima, successful command exit without verified enforcement disqualifies that configuration, not rootless Engine in general. **[U]** Which guarantees hold on the actual target Linux installations remains unmeasured. [Rootless resource limits](https://docs.docker.com/engine/security/rootless/tips/#limiting-resources), [limitations](https://docs.docker.com/engine/security/rootless/troubleshoot/).

## Agent-run Docker and build tools

| Route | What it buys | Cost and limitation |
| --- | --- | --- |
| Host Engine socket in Agent | Full familiar Docker | **Refused input**, not an alternative: grants authority over the host engine and its other workloads/data. Rootless host socket still grants that daemon's authority. |
| sbx private Engine [D/O] | Docker build/run/Compose inside each VM; a private daemon was observed in v0.39 shell template | Per-Agent daemon/cache overhead. RC5 blobot image/tool contents are not established by that old template observation. |
| Conventional Docker-in-Docker [D/I] | Private nested daemon without host socket | Normal privileged outer-container route removes important protections against the shared daemon-host kernel; not equivalent to guest root behind a per-Agent VM. |
| Rootless Docker-in-Docker [D] | Non-root nested daemon | Docker's own `dind-rootless` recipe still requires outer `--privileged` to disable seccomp, AppArmor and mount masks. The name alone does not establish a hardened outer boundary. |
| Rootless BuildKit [D/I] | Image builds without giving the Agent the shared Engine socket | Build-only, not a replacement for arbitrary Compose/run. Containerized official recipe relaxes seccomp/AppArmor/system paths; `--oci-worker-no-process-sandbox` weakens process isolation and is discouraged upstream. |
| Dedicated local builder service [D/I] | Buildx remote driver can speak to a separately managed builder over Unix/TCP with TLS options | Extra service, identity, cache isolation, egress and lifecycle work. It must be per-Agent or explicitly isolate callers. Cloud builder would cross this effort's scope. |

Sources: [Docker-in-Docker guidance](https://docs.docker.com/engine/security/rootless/tips/#rootless-docker-in-docker), [BuildKit rootless source](https://github.com/moby/buildkit/blob/master/docs/rootless.md), [Buildx remote driver](https://docs.docker.com/build/builders/drivers/remote/), and [prior private-daemon observation](08-the-first-box-sbx.md#2-the-mailbox-door-blobot-probe-a-shell-bind-mounted-repo-a). No nesting workload was executed here. Per-Agent VMs around Engine could retain the original boundary, but that is a VM orchestration alternative with its own costs, not vanilla shared-Engine containers.

## Network enforcement and mailbox

**[D] sbx:** policies support host/port, wildcard domains and CIDR rules; non-HTTP TCP is allowed by destination IP/port. A local policy can be global or sandbox-scoped. Organization governance, when active, overrides the ability of local allows to grant access. Balanced includes broad development destinations; Locked Down requires explicit allows, including provider endpoints. Built-in kits add rules, so neither a preset's name nor one denied canary establishes the full boundary. [Local policy](https://docs.docker.com/ai/sandboxes/security/policy/), [network rule semantics](https://docs.docker.com/ai/sandboxes/governance/access-controls/network/).

**[D]** sbx documents internal policy-aware DNS, policy enforcement when a client ignores proxy variables via transparent interception, and network-layer UDP/ICMP blocking. Its log distinguishes forward, forward-bypass, transparent, network and browser-open paths. **[O]** Our RC5 tests establish the authenticated HTTP mailbox door, exact old-port revocation and scoped inventory with two Machines, **not** raw TCP/UDP, DNS exfiltration, redirects, IPv6, transparent bypass resistance or TLS behavior on every host. **[U]** Those remain appropriate bounded first-box/egress canaries. Do not relabel the older cooperative `curl` test as hostile-bypass verification. [Defaults](https://docs.docker.com/ai/sandboxes/security/defaults/), [monitoring](https://docs.docker.com/ai/sandboxes/governance/monitor-and-enforce/monitoring/), [RC5 mailbox evidence](14-sbx-mailbox-lifecycle.md).

**[D] Engine:** configuring proxy variables configures cooperating applications; it is not compulsory traffic interception. Linux Engine has bridge firewall integration with iptables or nftables; Docker warns against editing its generated rules and documents interaction hazards with ufw. **[I]** A selective-egress implementation needs either a network whose only outward path is a separately trusted broker, or complete host-side enforcement plus DNS/proxy handling. It must cover IPv4/IPv6, raw TCP, UDP/QUIC, alternate DNS, redirects and private/host destinations. A proxy editable by guest root is not the outside boundary. A single shared proxy must also prevent one Agent impersonating another. [Proxy configuration](https://docs.docker.com/engine/cli/proxy/), [firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

**[D]** An `--internal` bridge normally still lets containers reach services listening on its host bridge address or all addresses. Isolated gateway mode removes that bridge address. **[I]** Therefore “internal network plus proxy” is only a candidate design: inspect the complete topology and verify unauthorized host services are unreachable. **[U]** No such blobot Engine topology is implemented or measured. [Gateway modes](https://docs.docker.com/engine/network/port-publishing/#gateway-modes).

| Mailbox route | Evidence and consequence |
| --- | --- |
| sbx on Mac | **[O]** Guest `host.docker.internal:PORT` is translated by proxy to host `localhost:PORT`; a per-sandbox allow uses the latter spelling. Synthetic bearer arrives intact; revoked port gets 403 without host request. Current lifecycle refreshes on reopen. |
| sbx on Linux | **[D/U]** Same documented host-service route; no local Linux/KVM measurement here. |
| Engine via Desktop | **[D/U]** `host.docker.internal` is the supported host-service hostname. Docs' generic HTTP example does not establish blobot's exact loopback-only listener under the selected enforced network; test it rather than changing listener scope. |
| Native Linux Engine | **[D/I]** `host-gateway` maps to the host bridge address, not a listener bound only to 127.0.0.1. Need a tightly scoped relay/carrier or another designed route. Host network mode discards the required network separation, so is not a shortcut. |

Sources: [sbx local development](https://docs.docker.com/ai/sandboxes/workflows/development/), [Desktop host services](https://docs.docker.com/desktop/features/networking/networking-how-tos/), [native host-gateway](https://docs.docker.com/reference/cli/dockerd/#configure-host-gateway-ip), [host network semantics](https://docs.docker.com/engine/network/drivers/host/), and the RC5 evidence above.

**[I] Both routes:** the mailbox still needs per-Agent authentication, inbound readiness, no cross-Agent token sharing, revoked stale ephemeral doors and bounded retry/recovery. Network reachability is not mailbox authorization. Domain allowlists also cannot promise prevention of all exfiltration: an allowed provider, forge or registry can itself carry attacker-controlled content. Redirect destinations require independent checks; raw TCP allowed to an IP is not URL/method inspection. The actual allowlist and block transcript remain the existing egress ticket's work.

### Desktop hardening is an additional product, not vanilla Engine

**[D]** Docker Business offers Enhanced Container Isolation (user namespaces and additional syscall/mount protections), and air-gapped container controls. The latter require enforced organization sign-in and Settings Management, intercept only configured TCP ports, and document possible bypasses by advanced users. **[I]** These are fair alternatives to mention, but they do not prove per-Agent microVM equivalence or free cross-platform sbx policy parity. Adopting them would introduce subscription/admin dependencies and shared configuration changes. [ECI](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation/), [air-gapped containers](https://docs.docker.com/enterprise/security/hardened-desktop/air-gapped-containers/).

## Login and credential ownership

**[D]** Engine supplies no coding-CLI OAuth manager. **[I]** A CLI installed inside a container can own its login/state under that Agent's persistent home just as in a VM. All required runtime paths must actually reside there; preserving a volume cannot preserve an external keychain or an omitted path. A compromised CLI can read its own in-guest credentials. Host homes, credential files, environment secrets and signing sockets remain unmounted; this is neither automatic login reuse nor cross-Agent isolation of one intentionally shared account.

**[D] sbx built-ins:** current docs describe host-managed OAuth with sentinels for Claude Code, Codex, Cursor and Droid. Codex's built-in flow can authenticate before sandbox launch; Cursor's proxy intercepts its polling token exchange. Generic kit OAuth fields permit sentinel replacement and also `passthrough: true`, which sends real token responses into the guest. These behaviors must be distinguished, not collapsed into “tokens never enter a sandbox.” [Credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/), [Codex integration](https://docs.docker.com/ai/sandboxes/agents/codex/), [Cursor integration](https://docs.docker.com/ai/sandboxes/agents/cursor/), [kit OAuth fields](https://docs.docker.com/ai/sandboxes/customize/kit-reference/#oauth).

**[D/U] Important custom-kit caveat:** the official example extending built-in Claude explicitly says proxy-managed OAuth is unsupported for the extended agent and prescribes API-key setup. That is a restriction on **that documented extension route**, not proof that every custom root kit is incapable of OAuth. It does mean inheriting fields or choosing a custom image does not establish support. Blobot's own root kit/image remains unverified for the preferred smooth proxy-managed flow, exactly as the first-box ticket already records. OpenCode's multi-provider behavior and fx's non-built-in integration cannot inherit the Codex result. [Kit examples](https://docs.docker.com/ai/sandboxes/customize/kit-examples/#fork-an-existing-agent).

**[D]** sbx service secrets can be global; existing sandboxes need scoped updates rather than automatically receiving a changed global secret. **[I]** Host-side proxy storage avoids direct token reads, but an authorized sandbox can still exercise the account through injected requests. One shared proxy login therefore changes the current per-Agent login grain. The author already allowed considering that route; its measurement and explicit grain amendment are still required. [Secret scope](https://docs.docker.com/ai/sandboxes/workflows/authentication/), [binding decision](../issues/08-detection-and-remedies-per-machine.md#decided-2026-09-05--the-engines-own-store-is-the-clis-file-not-blobots-database).

**[I/U] User flow on either engine:** device-code polling may avoid inbound callback routing; loopback OAuth needs a reachable, scoped callback path. Those mechanisms differ by vendor/version. Keep the login PTY opaque and use fixed adapter-owned commands; clickable terminal links do not authorize parsing/capturing credentials. A completed process is not proof of sign-in, and sign-in is not proof of paid inference. Real per-runtime callback, expiry, refresh and session-resume checks remain unperformed here.

## Installation, accounts, offline use and terms

| Topic | Engine route | sbx route |
| --- | --- | --- |
| Platforms [D] | Native Linux packages cover multiple distros/architectures. macOS Linux containers need a VM distribution; Desktop is one, not Engine itself. | macOS 14+ Apple silicon; Windows 11 x64 with Windows Hypervisor Platform; Ubuntu 24.04+ x64/arm64 with KVM and group access. Nested virtualization needed when host is itself a VM. |
| Initial friction [D/I] | Install/start VM distribution or Linux daemon, permissions and optional rootless prerequisites; acquire image. Existing compatible engine can reduce this. | Install standalone sbx; no Desktop needed; Docker browser sign-in; compatible engine/kit/image; currently shared SSH disable/restart admission. |
| Account [D] | Desktop does not require sign-in by default; organizations can enforce it. Registry/private image authentication is separate. | Docker account is required even for local execution; vendor explicitly calls this a business decision. |
| Offline [D/U] | Desktop documents offline operation except network/sign-in features. **[I]** Cached local images/workloads avoid registry dependency; provider inference may still need internet. | Local execution is not an unconditional offline guarantee. Exact current login-expiry grace, renewal cadence and behavior after long disconnection are **unverified**, not “offline forever” or “network on every exec.” |

A PAT is still a credential, and is not blobot's alternate storage mechanism. No account was logged out or expired and no network was disabled to test this question.

**[D] Licensing:** Engine's open-source license is separate from a distribution's terms. Docker's current docs say standalone sbx is free for commercial use, with paid organization governance; its release repository calls it proprietary and its LICENSE reserves rights. Desktop is free for personal/educational/non-commercial OSS and small-business use below both stated thresholds, with paid subscription requirements outside that scope, including government entities. “Engine is open source” does not waive Desktop licensing. [Engine license context](https://docs.docker.com/engine/install/#licensing), [sbx pricing statement](https://docs.docker.com/ai/sandboxes/), [sbx repository/license](https://github.com/docker/sbx-releases), [Desktop license](https://docs.docker.com/subscription/desktop-license/).

Neither a free-use statement nor an image redistribution clause establishes permission to repackage the proprietary sbx binary inside blobot. **[U]** Exact application to our installer/bundling/distribution and RC rollout needs legal/vendor confirmation before shipping. This report is not legal advice. Using an official user-authorized installer remains distinct from redistributing a binary. Image/CLI licenses, signing, notices and update delivery must be checked for either route.

**[O/I] Updates and telemetry:** previous sbx installation showed that changing Homebrew channels can stop the shared daemon. The staged app supplies `SBX_NO_TELEMETRY=1` to its clients; that does not certify unrelated invocations or all vendor/account network traffic. Engine/VM distribution updates likewise need compatible API/profile checks and care for unrelated workloads. A production channel cannot be selected from the success of one local RC fixture. ## Product consequences and later human trade-offs

**[I] Friction that can disappear with Engine:** sbx's required account, its RC-specific kit/admission quirks, and migration work caused by unsupported local volume reattachment/limit updates. **Friction that moves:** VM distribution setup on macOS, restrictive network broker/firewalls, private build environment, configuration inspection and their updates. **Friction that stays:** runtime installation/login, image download, per-Agent state ownership, scope-safe Workspace transfer, warning before interruption, sleep/wake correctness, stale data recovery and truthful power/readiness.

The user-facing flow can remain install → create Agent → work, with automatic defaults and later CPU/RAM adjustment, whichever engine is chosen. Existing green/gray power-dot and sleep policy are above the engine. Neither backend may wake a sleeping Machine merely to display login, claim engine readiness proves Agent login, silently run locally on failure, or restart unrelated workloads. These are existing contract obligations, not a new design decision in this report.

**[D/I] Shared files are security-bearing on both routes:** Docker's default sbx workspace/skills behavior is broader than blobot's closed list. Shared writable skills let one sandbox change another's future instructions; host stdio MCP services execute outside the VM. Blobot must retain its controlled image/kit and readonly authored-skills plan, not adopt vendor defaults for convenience. For Engine, readonly bind mounts still expose the selected bytes; they are not permission to mount a host home or whole source checkout. Returned branches remain untrusted code to review before host execution. [sbx security exceptions](https://docs.docker.com/ai/sandboxes/security/), [binding Machine amendments](../issues/01-what-a-machine-is.md#amendments-2026-09-05).

The later grill should decide, with the companion cost report:

1. Is a **shared-kernel, explicitly hardened container** acceptable for our hostile-Agent model, or does the selected per-Agent kernel remain required? A yes would reopen *What a Machine is*, the domain wording and engine/admission assumptions, then revisit the still-open highest-trust disclosure. It is not merely changing a CLI executable.
2. Must Agents retain general Docker/Compose and guest sudo, or is a narrower build-only/no-nesting workload acceptable? Which additional daemon/profile/broker costs fit the measured performance budget?
3. Which distribution/account/update requirements are acceptable for the promised setup flow, including disconnected use and production support? Free commercial sbx use and optional Desktop sign-in answer different questions.
4. Which verified login route is required before shipping: per-Agent CLI state, or the conditional engine-managed route with an explicit grain change? No assumed shared OAuth shortcut.

**Disqualifying evidence, not a decision already taken:** Engine fails the unchanged per-Agent-microVM requirement unless augmented with per-Agent VMs; a candidate configuration also fails if it needs host-socket exposure, unenforced limits, uncontrolled host/sibling reach or an untrusted egress broker. sbx fails our deployment route if no acceptable stable release can enforce the required SSH/mount boundary, if its account/offline/distribution terms are unacceptable, or if required runtime login cannot work without a forbidden credential practice. Either route fails if preservation/recovery cannot protect the two persistent trees or mailbox behavior breaks. Unknowns must be measured or accepted explicitly by the author, not erased by an adapter's small line count.

No downstream ticket, placement default, production guard, engine setting or selected engine was changed by this research.
